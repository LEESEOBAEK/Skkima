# 쓰끼마 고도화 구현 FAQ 및 권장 명세

버전: v0.1
상태: 구현 전 기준 명세
대상: Windows 개인 개발 환경
기준 앱: 쓰끼마 브라우저 연구실

## 1. 이 문서의 목적

이 문서는 쓰끼마에 추가하려는 다음 기능을 구현하기 전에 공통 기준을 고정하기 위한 문서다.

1. Chrome DevTools MCP 실제 연동
2. 브라우저 읽기와 조작의 승인 게이트
3. Firefly·Adobe·Blender 연동
4. 외부 스킬·플러그인 관리 고도화
5. 다중 프로젝트 실시간 감시
6. 로그인·팀 권한·거버넌스
7. 웹 근거 데이터 장기 보관·검색·백업

이 문서는 기존 워크플로 엔진이나 쓰끼마 앱을 교체하지 않는다. 기존 앱의 프로젝트, 작업 세션,
Run 기록, 산출물, 브라우저 읽기 근거를 유지하면서 외부 도구와 승인 흐름을 연결하는 확장 계층을
정의한다.

## 2. 한 문장 정의

쓰끼마는 사용자가 선택한 프로젝트 안에서 외부 도구의 상태와 읽기 결과를 근거로 기록하고,
승인된 작업만 외부 프로그램에 전달하며, 결과와 사람의 검토를 다시 프로젝트 기록으로 남기는
로컬 우선 작업 운영 앱이다.

## 4. 현재 구조와 추가 계층

### 현재 유지되는 영역

- Tauri 데스크톱 창과 쓰끼마 UI
- 프로젝트 폴더와 작업 세션
- 독립·이어가기·분기 Run 관계
- Workflow 산출물과 검증 결과
- WebView2 브라우저 읽기 기능
- Chrome Bridge의 읽기 근거 기록
- 플러그인·스킬 라이브러리와 프로젝트 설치
- 아카이브와 로컬 환경 진단

### 새로 추가되는 영역

1. Connection Layer: 외부 도구 연결과 상태 확인
2. Capability Layer: 읽기, 미리보기, 조작 가능 범위 표현
3. Approval Layer: 실행 전 승인과 승인 무효화
4. Adapter Layer: Chrome, Firefly, Adobe, Blender별 연결 구현
5. Evidence Layer: 입력, 실행, 결과, 검토 근거 연결
6. Governance Layer: 사용자·프로젝트·팀 권한과 정책
7. Retention Layer: 보관, 검색, 백업, 삭제 정책

## 5. 기능별 FAQ

### 5.1 Chrome DevTools MCP 실제 연동

#### Q. 왜 현재 `external_connections.rs`만으로는 충분하지 않은가?

현재 파일은 별도 Chrome의 localhost DevTools endpoint가 응답하는지 확인하는 진단 모듈이다.
브라우저 버전과 WebSocket 주소를 확인하지만, MCP 세션을 생성하거나 페이지를 조작하지는 않는다.

#### Q. 무엇을 추가해야 하는가?

- MCP 서버 연결 상태 확인
- 사용 가능한 도구 목록 확인
- 브라우저 탭과 대상 페이지 식별
- 읽기 요청 전달
- 응답을 쓰끼마 근거 형식으로 변환
- 연결 종료와 오류 기록

#### 권장 범위

첫 단계는 `연결 확인 → 현재 탭 읽기 → 구조 요약 → 쓰끼마 근거 저장`까지만 구현한다.
클릭, 입력, 제출, 파일 업로드는 다음 승인 게이트가 완성된 뒤 추가한다.

### 5.2 브라우저 읽기·조작 승인 게이트

#### Q. 읽기와 조작을 왜 분리하는가?

페이지 구조를 읽는 것은 정보 수집이지만, 클릭·입력·제출은 외부 상태를 바꿀 수 있다.
두 작업을 같은 권한으로 처리하면 사용자가 승인한 범위와 실제 실행 범위를 구분하기 어렵다.

#### 권장 상태 흐름

```text
disconnected
  -> connected
  -> inspected
  -> action_proposed
  -> waiting_for_approval
  -> approved
  -> executing
  -> result_collected
  -> human_reviewed
```

실패나 불명확한 결과는 자동 재실행하지 않고 `blocked` 또는 `needs_review`로 남긴다.

#### 권장 승인 규칙

- 읽기는 기본 허용
- 외부 상태를 바꾸는 조작은 항상 승인 필요
- 승인 대상은 사이트, 탭, 조작 종류, 입력값, 대상 요소, 실행 횟수다.
- 승인 이후 주요 값이 바뀌면 승인을 무효화한다.
- 로그인 여부는 확인할 수 있지만 비밀번호와 쿠키를 저장하지 않는다.
- 제출·결제·게시·삭제는 기본 차단한다.

### 5.3 Firefly·Adobe·Blender 연동

#### Q. 세 가지를 한 번에 구현하는 것이 좋은가?

아니다. 외부 프로그램마다 인증 방식, 화면 상태, 파일 처리, 결과 확인 방식이 다르다.
공통 어댑터 인터페이스를 먼저 만들고 하나씩 연결해야 실패 원인을 분리할 수 있다.

#### 권장 순서

1. Chrome DevTools MCP 읽기
2. 브라우저에서 단일 저위험 조작
3. Firefly 단일 이미지 생성 요청의 계획·승인·결과 기록
4. Adobe 작업 결과 확인과 파일 근거 기록
5. Blender 명령 실행 전 미리보기와 결과 파일 수집

#### MVP에서 제외할 것

- 자동 게시
- 결제 또는 유료 생성 요청
- 여러 장 일괄 생성
- 백그라운드 무인 실행
- 파일 삭제·덮어쓰기
- 계정 간 자동 전환

### 5.4 외부 스킬·플러그인 관리

#### Q. 외부 저장소 전체를 설치해도 되는가?

아니다. 저장소 전체가 여러 스킬과 실행 코드를 포함할 수 있으므로, 먼저 목록을 읽고 사용자가
선택한 항목만 등록해야 한다.

#### 권장 구조

- Library: 외부 원본의 읽기 전용 스냅샷
- Skill Registry: 이름, 설명, 원본 URL, 커밋, 해시, 상태
- Project Install: 선택한 프로젝트에 설치된 스킬
- Compatibility: Codex, Claude Code, Antigravity 등 플랫폼별 인식 상태
- Smoke Test: 실제 인식 여부를 확인하는 제한된 테스트

#### 권장 안전 규칙

- 원본 저장소의 실행 코드를 자동 실행하지 않는다.
- 스킬 파일과 실행 파일을 구분한다.
- 설치 전 원본 커밋과 해시를 기록한다.
- 프로젝트별 설치를 기본으로 하고 전역 설치는 선택 사항으로 둔다.
- 업데이트 전 이전 스냅샷을 보존한다.
- 설치된 스킬이 작업에 사용되었는지 Run 기록에 남긴다.

### 5.5 다중 프로젝트 실시간 감시

#### Q. 바로 여러 프로젝트를 동시에 감시해야 하는가?

아니다. 현재 앱은 선택한 프로젝트를 안정적으로 읽고 표시하는 것이 우선이다.
다중 감시는 파일 변경, 프로세스 상태, 외부 Run 상태를 동시에 다루므로 별도 수명주기 설계가 필요하다.

#### 권장 단계

1. 현재 프로젝트의 수동 새로 고침
2. 선택 프로젝트의 제한된 파일 감시
3. 최근 프로젝트의 상태 요약 갱신
4. 여러 프로젝트의 이벤트 큐와 오류 표시
5. 백그라운드 감시와 알림

각 프로젝트는 서로 다른 상태, 권한, 오류를 가지므로 하나의 전역 상태로 합치지 않는다.

### 5.6 로그인·팀 권한·거버넌스

#### Q. 개인용 앱에 로그인 기능을 바로 넣어야 하는가?

아니다. 개인 로컬 단계에서는 로그인보다 데이터 경계와 권한 모델을 먼저 정의하는 것이 중요하다.
비밀번호를 직접 저장하는 방식은 사용하지 않는다.

#### 권장 순서

1. 개인 로컬 사용자와 프로젝트 소유자 구분
2. 프로젝트별 읽기·실행·승인 권한 정의
3. 승인자와 실행자를 별도 기록
4. 팀 기능이 필요할 때 외부 인증 제공자 연동 검토
5. 서버 저장소와 감사 로그 추가

Google 로그인 등 외부 인증을 사용하더라도 앱은 비밀번호를 보관하지 않고, 인증 결과와 최소한의
사용자 식별자만 사용해야 한다.

### 5.7 웹 근거 데이터 장기 보관·검색·백업

#### Q. 현재 JSON 기록만 계속 쌓으면 충분한가?

초기 실험에는 충분하지만, 기록이 많아지면 같은 URL의 여러 관찰과 페이지 변경을 구분하기 어렵다.

#### 권장 보관 단위

- Observation: 특정 시점의 페이지 구조 관찰
- Revision: 같은 대상의 구조 변경 버전
- Evidence: 작업에 사용된 근거 묶음
- Action Record: 읽기 또는 조작 요청
- Review Record: 사람이 확인한 결과

#### 권장 보관 규칙

- URL, 제목, 구조 해시, 캡처 시각, 출처를 기록한다.
- 비밀번호, 쿠키, 토큰, 입력값은 저장하지 않는다.
- 같은 구조의 반복 읽기는 하나의 관찰에 누적한다.
- 구조가 바뀌면 새 revision을 만든다.
- 프로젝트별 보관과 전체 검색을 분리한다.
- 원본 기록 삭제와 인덱스 삭제를 구분한다.
- 백업 복원 테스트를 별도로 수행한다.

## 6. 통합 처리 흐름

```text
프로젝트 선택
  -> 연결 대상 선택
  -> 연결 상태 확인
  -> 읽기 또는 작업 계획 생성
  -> 근거·대상·범위 검증
  -> 사용자 승인
  -> 단일 어댑터 실행
  -> 결과 수집
  -> 사람 검토
  -> Run·산출물·근거에 연결
  -> 보관·검색·백업
```

MCP는 이 흐름의 연결 수단이며, 최종 상태와 승인 기록의 원본이 아니다. 최종 기록은 쓰끼마
프로젝트와 Workflow Run에 남긴다.

## 8. 금지되는 자동화

- 승인 없는 외부 조작
- 로그인 정보 또는 비밀번호 저장
- 결제·이체·구독
- 게시·전송·삭제
- 불명확한 실행 결과의 자동 재시도
- 검증되지 않은 저장소의 코드 자동 실행
- 사람 검토를 대체하는 법률·금융·상업 판단

## 9. 구현 전환 조건

각 단계는 다음 조건을 만족해야 다음 단계로 넘어간다.

1. 읽기 결과가 프로젝트와 Run에 연결된다.
2. 승인 없이 조작 어댑터가 호출되지 않는다.
3. 승인 후 계획 변경 시 재승인이 요구된다.
4. 실패·중단·연결 끊김이 복구 가능한 상태로 기록된다.
5. 결과 파일과 근거가 같은 실행 계보로 연결된다.
6. 민감정보가 저장되지 않는 테스트가 통과한다.
7. 사용자가 화면에서 현재 상태와 다음 행동을 이해할 수 있다.

## 10. 추론 QA: 사용자 의견이 필요한 결정

아래 항목은 기술적으로 임의 결정하면 사용 방식이 달라지므로 1차 사용자 확인이 필요하다.

### QA-01. 조작 범위

권장: 읽기와 미리보기부터 시작하고, 실제 조작은 단일 저위험 작업만 허용한다.

확인할 내용: 첫 조작 대상으로 클릭, 텍스트 입력, 파일 선택 중 어디까지 허용할 것인가?

### QA-02. 승인 방식

권장: 외부 상태를 바꾸는 작업은 매번 승인한다.

확인할 내용: 사용자가 이미 승인한 동일 작업을 반복할 때도 매번 승인할 것인가, 짧은 시간 동안만
반복 승인을 허용할 것인가?

### QA-03. 로그인 세션

권장: 사용자가 직접 로그인한 별도 Chrome 프로필을 쓰끼마가 확인만 한다.

확인할 내용: 기존 Chrome 프로필을 사용할 것인가, 자동화 전용 별도 프로필을 사용할 것인가?

### QA-04. 첫 외부 도구

권장: Chrome DevTools MCP 읽기와 단일 조작을 먼저 검증한다.

확인할 내용: 첫 실사용 대상은 Chrome 웹 페이지인가, Firefly 이미지 생성인가?

### QA-05. 프로젝트 감시 우선순위

권장: 선택된 한 프로젝트를 안정적으로 감시한 후 다중 프로젝트로 확장한다.

확인할 내용: 다중 프로젝트 감시가 실제 사용에서 즉시 필요한가, 아니면 외부 도구 연동이 먼저인가?

### QA-06. 스킬 신뢰 정책

권장: 외부 저장소는 선택한 스킬만 수동 승인 후 설치한다.

확인할 내용: 개인이 직접 확인한 저장소만 허용할 것인가, 공개 저장소 검색과 추천까지 허용할 것인가?

### QA-07. 팀 기능 시점

권장: 개인 로컬 기능을 먼저 완성하고 팀 권한은 후속 단계로 둔다.

확인할 내용: 가까운 시기에 다른 사용자가 실제로 사용할 예정인가?

### QA-08. 보관 기간

권장: 프로젝트별 로컬 보관을 기본으로 하고, 삭제 전 백업만 제공한다.

확인할 내용: 웹 근거 기록을 장기 보관해야 하는 업무나 법적 요구가 있는가?

## 10-1. 권장안 고정 결과

사용자가 권장 방향으로 진행하기로 했으므로 아래 기본값을 구현 기준으로 확정한다.

| QA | 확정 기준 |
|---|---|
| QA-01 | 초기 조작은 단일 클릭부터 시작하고, 최종적으로 텍스트 입력·파일 선택까지 확장 |
| QA-02 | 읽기는 자동 허용, 외부 변경은 Codex식 단계형 승인, 고위험 작업은 항상 재승인 |
| QA-03 | 사용자가 직접 로그인한 기존 Chrome 프로필 사용, 인증 정보는 저장하지 않음 |
| QA-04 | Chrome DevTools MCP 읽기와 단일 클릭을 첫 실사용 대상으로 선택 |
| QA-05 | 현재 선택한 프로젝트 하나를 먼저 감시하고 이후 다중 프로젝트로 확장 |
| QA-06 | 사용자가 확인한 저장소의 선택 스킬만 등록하고 출처·커밋·해시를 보존 |
| QA-07 | 개인 로컬 기능을 먼저 완성하고 팀 권한·서버 인증은 후속 확장 |
| QA-08 | 프로젝트별 로컬 보관을 기본으로 하며 사용자가 실행하는 백업·복원을 지원 |

이 결정으로 일반적인 UX·데이터 구조·구현 순서에 대해서는 추가 질문을 반복하지 않는다.
다만 결제, 게시, 삭제, 계정 권한 변경, 개인정보 처리처럼 되돌리기 어렵거나 법적 영향이 있는
작업은 실제 실행 직전에 별도 확인을 요구한다.

최종 제품 범위는 QA-01의 초기 단일 클릭에 제한되지 않는다. 단일 클릭으로 승인·근거·복구
구조를 검증한 뒤 텍스트 입력, 파일 선택, Firefly·Adobe·Blender 어댑터까지 전체 기능을
완성하는 것을 목표로 한다.

## 11. 권장 구현 순서

### 묶음 A: 브라우저 연결과 승인 기반

1. Chrome DevTools MCP 연결 계약 확정
2. 읽기 요청과 근거 저장 연결
3. ActionProposal과 ApprovalRecord 추가
4. 단일 저위험 조작과 결과 기록

### 묶음 B: 외부 도구 어댑터

5. Firefly 단일 생성 어댑터
6. Adobe 또는 Blender 중 하나를 선택해 파일 결과 수집
7. 공통 어댑터 오류·복구 규칙 정리

### 묶음 C: 스킬·프로젝트 운영

8. 외부 스킬 선택 설치와 업데이트 스냅샷
9. 선택 프로젝트 감시와 이벤트 기록
10. 근거 검색·revision·백업

### 묶음 D: 조직 기능

11. 사용자·역할·승인자 모델
12. 외부 인증 제공자 연동
13. 팀 저장소와 감사 로그

## 12. 명시적 제외 범위

- 첫 단계에서 모든 MCP 서버를 지원하지 않는다.
- Firefly·Adobe·Blender를 동시에 완성하지 않는다.
- 쓰끼마가 사용자의 비밀번호를 관리하지 않는다.
- 자동 게시·결제·삭제를 구현하지 않는다.
- 팀 서버와 실시간 협업을 개인 로컬 MVP에 포함하지 않는다.
- 원격 데이터베이스를 먼저 도입하지 않는다.

## 13. 현재 판단

현재 구조는 7개 기능을 추가할 수 있는 기반을 이미 갖추고 있다. 다만 핵심은 MCP 기능을 많이 붙이는 것이
아니라, 읽기 결과와 외부 조작 사이에 승인·근거·복구 계층을 두는 것이다.

따라서 다음 구현은 묶음 A부터 시작하되, 위의 권장 기본값을 그대로 적용한다. 묶음 A의
연결·읽기·승인·단일 조작이 통과하면 묶음 B의 외부 도구 어댑터, 묶음 C의 운영 관리,
묶음 D의 팀 기능 순서로 확장한다. 각 묶음은 독립적으로 실행 가능하고 이전 기록과 호환되어야 한다.
